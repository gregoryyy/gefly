## Quality findings (medium)

**PR #28a, assurance tooling**

1. `utils/assure/src/status.ts`: a DONE `TODO:` clause counts as a completion record
   unless it contains `remain|remains|future|parent|open|deferred`. A ticked task whose
   only DONE mention says "in progress" therefore passes the AS2 check. No negative
   fixture covers this.
2. `utils/assure/src/evidence.ts` (`inspectAircraft`): the source applicability field
   is stored but never compared with the aircraft, so a datum from a generic 172P source
   marked `sourced` counts as 172S evidence (AS3).

**PR #28b, documentation and status**

3. `docs/design/EXERCISE-01.md` still proposes "E7 or a dedicated E14", which collides
   with the new E14 assurance section in EVAL.
4. In EVAL E0-CI, CI5 (runner's preinstalled Node) and CI2 (phase list) contradict the
   SBOM and README text about setup-node and Node 26 and the new assurance phase.
5. In `docs/design/BRIEFING.md` §5, the proposed new requirements R-BRIEF-2 and R-COMM-2
   were relabelled as criteria under R-BRIEF-1 and R-COMM-1 without a recorded decision.

**PR #30, browser prototype**

6. The SBOM CesiumJS row says it was "Adopted through the application lockfile", but
   the app neither locks nor imports Cesium.
7. The missing-engine smoke check aborts `worker.js` instead of the absent
   `dist/jsbsim.{mjs,wasm}` files, so the documented failure hint is unverified.
8. The packet does not show how `just build-flight-engine` output reaches the path that
   `just fly` serves: `build.sh` was not supplied, and CI does not build the engine.

The dispatcher spot-checked findings 1, 3, 5 and 6 at main and found each one present.
The other findings were not independently verified. Low findings, such as diagnostic
assertions, fixture gaps, locale-dependent sorting, ulp-level boundary wording, lockfile
provenance and stale README/SBOM phrasing, are listed in the JSON.
