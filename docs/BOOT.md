How a new project gets set up, from raw idea to a repository that agents and people can work in. Propeller was set up this way on 2026-10-25 between 10:20 and 11:00, following the conventions of the kibitz repository. Use this as the checklist for the next project. Status: 2026-10-27 15:18.

## The steps

| # | Step | Produces | Propeller commit |
| --- | --- | --- | --- |
| 1 | Collect the input | `docs/input/`, `.gitignore` | Add reference input |
| 2 | Assess it critically, state the idea, list the gaps | `docs/IDEA.md`, `docs/GAPS.md`, notes in the first DONE entry | Add IDEA, ARCH and GAPS (added later) |
| 3 | Write the design concept and its security implications | `docs/design/`, `docs/SEC.md`, `AGENTS.md`, `CLAUDE.md` | Add design concept; SEC added later |
| 4 | Plan the architecture, evaluations and work | `docs/ARCH.md`, `docs/EVAL.md`, `docs/TODO.md`, `docs/ROAD.md`, `docs/DONE.md` | Add plan, roadmap and progress log; ARCH and EVAL added later |
| 5 | Make it readable and buildable; set the process and conventions | `README.md`, `justfile`, `utils/pdf/`, this file; `docs/SDLC.md`, `docs/STYLE.md`, `docs/SBOM.md`, PR template, `.editorconfig` | Add README, document builds and bootstrap guide; SDLC, STYLE and SBOM added later |
| 6 | Put it under version control | Git repo, private GitHub remote | (all of the above) |
| 7 | Start the foundation, then TODO mode | Remaining TODO 0 items, then TODO 1 onwards in TODO mode | Feature branches and PRs from here on |

### 1. Collect the input

Put the raw material in `docs/input/`: original notes, conversations with other assistants, sketches, links. Don't edit it later. It's the record of where the idea came from, and later documents cite it. Decide whether it belongs in the repository. Kibitz keeps it out (ignored); Propeller keeps it in a private repository.

### 2. Assess it critically

Before designing anything, read the input as a reviewer. Separate the claims that survive (here: "the target is the next conversation", "transpose before summarising") from flattery and invented market gaps. Check the competitive landscape as it is today. Write down what the product has to beat. The reasoning goes into the first DONE entry, and the result into `docs/IDEA.md`: the purpose of the software, its intended users and the added value for them, and the approach, including the innovation pursued if there is one. Be honest there about what isn't new.

Start `docs/GAPS.md` at the same time. It lists **questions** for the user (numbered `Q1` …, each with why it matters, a proposed answer where there is one, and an answer line) and **assumptions** that seemed clear enough not to ask (`A1` …, each with its basis and a correction column). The user answers the questions and checks the assumptions. **Every answer is recorded with date, time and author**; if an answer changes, the new one goes on top and the earlier ones stay, struck through, with their date, time and author, so nothing is overwritten silently. Answered entries move into the document they affect and get a `Resolved` line saying when, by whom and where. Questions that block a milestone are marked blocking. Keep GAPS current through every later step.

### 3. Write the design concept

`docs/design/` holds the documents of central importance, so their names are upper case:
- `CONCEPT.md`: the insight, the model, the interaction ideas, the role of AI, what to beat, how to measure it, open questions.
- One document per approach or product variant (here `PERSONAL.md` and `ENTERPRISE.md`), each with scope, mockups, and the gates for going on.

Mockups are ASCII in fenced `text` blocks, generated by a small script so every bordered row has the same length. Keep them at 100 columns or fewer.

Write `docs/SEC.md` next to the concept: the assets, data protection obligations, threats with their consequences for the design, controls by phase and how they're verified. Security decisions shape the design (what may reach an AI model, where data lives), so they belong at the start, not before release.

At the same time, write `AGENTS.md`: what the project is, layout, stack (or "not decided"), process, docs conventions, the design rules that need a deliberate decision to change, and security. `CLAUDE.md` contains only `@AGENTS.md`, so every agent reads the same rules.

### 4. Plan

- `docs/ARCH.md`: the architecture to be built. Principles, components, data model, flows, deployment by phase, trust boundaries, performance budgets and open decisions. It describes the target before code exists and is updated whenever an architectural decision is made.
- `docs/EVAL.md`: evaluations of the project's claims and proposed benefits. Define the questions or hypotheses, comparison baselines, fixtures or datasets, procedure, measures, success and stop criteria, and limitations before running them. Link the requirements or decisions being tested and the commands or scripts that reproduce the evaluation. Distinguish proposed targets from observed results. TODO schedules the work; EVAL defines how to evaluate it; RESULTS and DONE record findings and the resulting decisions.
- `docs/TODO.md`: the plan. Numbered milestones (`## 1. …`), tasks (`1.1`) and subtasks (`1.1.1`) with checkboxes. Milestone 0 is always project setup and initial inputs: the steps in this file, ticked as they're done, plus what's left of them (answers to blocking questions, PR template, licence). Milestone 1 is the foundation: quality gates, stack decision, shared model, fixtures, visual or technical basics. Tag choices as *(decision)* and alternatives as *(variant)*. Never renumber.
- `docs/ROAD.md`: the higher-level roadmap. Phases with a goal and a measured gate each, plus ideas that aren't scheduled. A phase becomes TODO milestones when it starts.
- `docs/DONE.md`: the progress log, newest entry on top. `## YYYY-MM-DD HH:MM — Title` (time of day to the minute, since projects move fast), TODO items and PR, the agent that did the work (`Agent: Opus 5.5, reasoning: High, subagents: none.`), then **Implementation notes**, **Deviations** and **Insights**. Start it with entries for the steps already taken.

When the first work is studies or prototypes, frame each by one question and end it with a recorded review. That keeps exploration from turning into an unplanned product build.

### Subprojects and document precedence

Each subproject may have its own version of any standard document: for example,
`<subproject>/docs/IDEA.md`, `ARCH.md`, `EVAL.md`, `GAPS.md`, `TODO.md`, `ROAD.md`,
`DONE.md`, `SEC.md`, `SDLC.md`, `STYLE.md` or `SBOM.md`. A subproject's version supersedes
the corresponding root document within its declared scope. Root documents remain the
defaults where no local version or more specific rule exists; other subprojects are unaffected.

Create only the local documents the subproject needs. Each local document states what it
supersedes and which root conventions it inherits, and the subproject README links to them.
Keep each task, evaluation protocol and result authoritative in one place; root overviews
link to local records instead of duplicating their status. Qualify local task and question
references with their document or subproject so their numbers are unambiguous.

Upstream example: Propeller's `semgit/docs/EVAL.md` defines its attribution/review
experiment in place of the root protocol, with its work tracked in root TODO 12.
That subproject is not part of Gefly.

### 5. Make it readable and buildable

- `README.md`: what it is in two paragraphs, status, a map of the documents, how to build, layout.
- `justfile`: one entry point for everything. From the start it has the document builds: `just docs` writes an A4 PDF next to every Markdown file (`foo.md.pdf`) with pandoc and headless Chrome, incrementally. pandoc's intermediate HTML is not kept. Math in GitHub syntax becomes MathML; ```` ```latex ```` blocks (TikZ, tables) are typeset to SVG by `utils/pdf/latex.lua`. Recipes for serving, checking and testing are added when the stack is decided.
- `utils/pdf/`: `style.css` and `mermaid.html` for the document builds, copied from kibitz, plus `latex.lua` for LaTeX insets.
- `docs/SDLC.md`: the development process that AGENTS.md refers to: lifecycle, work items, branches and PRs, definition of done, testing, studies, TODO mode, decisions, releases.
- `docs/STYLE.md`: code style, interface conventions (behaviour, visual language, accessibility, copy, AI-generated text) and written output (documents, commits, PRs, agent replies).
- `docs/SBOM.md`: rules and criteria for software and libraries, the toolchain, the major dependencies, and where the package managers keep the details. Dependency updates are automated; SBOM.md is the overview.
- `.github/pull_request_template.md` with the definition-of-done checklist, and `.editorconfig`.
- `docs/research/README.md`: the index and format for research notes that clarify gaps or other questions during design and implementation. Research informs; decisions stay with GAPS and the affected documents.
- Optionally `docs/assure/ASSR.md`: how much traceability the project wants, from requirements and gaps to artifacts and tests, and at which level (conventions, generated graph, database with agent hooks).
- `.gitignore`: generated documents (`*.md.pdf`, `.pdfstamps/`), dependencies, secrets (`.env*` except `.env.example`), caches, test output, OS and editor files.

### 6. Put it under version control

```bash
git init -b main
# one commit per step above, so the history tells how the project came about
gh repo create <name> --private --source . --remote origin --push
```

If a remote of that name already exists, look at it before replacing it. After the initial commits, `main` is only changed through PRs (AGENTS.md).

### 7. Start the first milestone

Work on TODO 1 on feature branches: CI, PR template, licence, stack decision. Each PR ticks its TODO items and adds a DONE entry.

## TODO mode

Once the foundation is in place, the remaining work can be handed to a coding agent by starting **TODO mode** with one message:

> **TODO mode:** Work through the remaining TODO.md milestones in order, completing required tests and documentation and opening a separate PR for each milestone. Continue until all actionable milestones are complete or a documented blocker requires user input.

This works because the setup above gives the agent everything it needs:
- **What to do:** TODO.md, in order, with numbered items it can reference.
- **How to do it:** AGENTS.md: branches, tests, docs conventions, design rules, security.
- **When it's done:** each milestone is one PR with its tests passing, its TODO items ticked and a DONE entry on top.
- **When to stop:** a blocking GAPS question, a *(decision)* item the agent can't settle from the docs, a failing gate, or missing access. It records the blocker in GAPS.md, DONE.md and the PR, then asks for input.

TODO mode is part of the development process; [SDLC](SDLC.md#todo-mode) is where its rules are maintained, including how milestone PRs are based so they merge cleanly in order.

Review the PRs as they come in. A deviation recorded in DONE.md is the agent's way of saying where the plan didn't survive contact with the code.

## Options

Three parts of Propeller's setup are worth taking into other projects. They're optional: adopt them when the project benefits.

### `assure/`: assurance and lineage

Traceability from requirements and gaps to plan, results and code, as described in [ASSR](assure/ASSR.md):
- **Design** in `docs/assure/ASSR.md`: the lineage graph, three levels (conventions, generated graph with checks, fact store kept current by agent hooks or a subagent), how to keep the graph right, risks.
- **Level 1 conventions:** requirement IDs (`[R-AREA-n]`) at the end of the statements they define, `Refs:` trailers on every commit, test titles that start with the requirement they verify. `just reqs` and `just refs` read them back.
- **The tracker** in `assure/`, specified in `docs/assure/SPEC.md`: a small TypeScript package (run by Node directly) with a typed fact schema, an append-only store, extractors for documents, plan, history, code objects and tests, an append-only ledger for confirmations, checks with severities, and `trace`, `diff`, `report`, `graph` and `sample`. CI runs `node assure/src/cli.ts check` and puts the report in the job summary.

Copy `docs/assure/ASSR.md` and `assure/`, choose a level, and add the conventions to SDLC and STYLE.

**In the CI toolchain.** The tracker needs only Node and Git, so it fits into any project's CI as a gate:
- a job that checks out the whole history (`fetch-depth: 0`, since the checks read `Refs:` trailers from every commit), runs `npm ci` and the tests in `assure/`, then `node assure/src/cli.ts check`, which fails on errors;
- `node assure/src/cli.ts report >> "$GITHUB_STEP_SUMMARY"` for the report in the job summary, and `assure diff origin/main` for the lineage diff in the PR description;
- locally, the same check in `just check`.

Propeller's `.github/workflows/ci.yml` has this job (*Assurance*); `assure/example.pdf` (upstream Propeller artifact) is a printout of a real run (PR #38): the job summary with the lineage report (5,161 facts; 112 of 117 requirement claims in commits backed by their changes), the problems by severity, and the coverage table per requirement. A project can start with the check as a warning and make it blocking once the conventions are in place.

The supplied `assure/example-7ce5959.md` report (upstream Propeller revision `7ce5959`) accompanies the
PDF. Both are historical examples; their counts and findings describe that revision.

**When the hosted CI is unavailable.** Keep the workflow file as the one definition and run it locally, as Propeller did when GitHub Actions stopped starting jobs (TODO 0.8): `utils/ci/` reads the workflow from the commit, runs its `run:` steps in a clean worktree of that commit, maps each action to a local equivalent (checkout, setup-node, cache, upload-artifact, gitleaks) and stops on any step it can't map. `just ci --post` sets a commit status per job (`local / <job name>`) through the GitHub API, which works without Actions; the prefix keeps it apart from the Actions check of the same job. Keeping the workflow to plain `run:` steps keeps it runnable both ways.

### Upstream option: Claude Code subagents and hooks

For Gefly, the required role split in the extension below supersedes the example
role table in this optional upstream section. No hooks are installed or claimed.

With a coding agent doing most of the work (TODO mode), two Claude Code features keep it on the rails: **subagents** take on jobs that need their own context or an independent view, and **hooks** enforce the rules mechanically, so they hold even when the agent forgets them. Subagents live in `.claude/agents/*.md`, hooks in `.claude/settings.json` (checked in); the hook scripts belong in `utils/hooks/` with tests.

**Subagents, by use case:**

| Agent | Use case | Tools | Why separate |
| --- | --- | --- | --- |
| **Implementer** | Writes a TODO item's code and tests; fixes a failing check from its output | All | Keeps the orchestrating context small |
| **Assurance** | At the end of a milestone: reviews declared links, places missing ones, checks the design rules, SEC and the definition of done, writes the security impact and lineage part of the PR, raises GAPS questions ([ASSR](assure/ASSR.md#the-assurance-agent)) | Read, search, `git diff`, the tracker | Must not be the author: it gets the diff and the requirement texts, not the author's reasoning |
| **E2E runner** | Runs Playwright and the screenshot scripts, looks at the frames, returns only failures and bad frames | Shell, read | Long test output stays out of the main context |
| **Gap researcher** | Writes one research note on one GAPS question in `docs/research/` | Read, web, write in `docs/research/` only | Research informs; it doesn't decide |

An **orchestrator** can run TODO mode with very little intelligence of its own: a plain script that picks the next milestone, branches, runs the checks, commits, opens the PR, and calls the agents only where judgement is needed, mapping their structured results to fixed next steps with bounded retries.

**Hooks, by use case:**

| Hook | Use case |
| --- | --- |
| **Stop** | Run the fast checks (lint, types, lineage, unit tests; seconds) before the agent ends a turn; on failure it keeps working |
| **PreToolUse on Edit and Write** | Deny edits to raw input (`docs/input/`); deny `innerHTML` and `dangerouslySetInnerHTML` in app code (untrusted text is never HTML); deny anything that looks like an API key or private key |
| **PreToolUse on Bash** | Block `git commit` on `main`, commits without a `Refs:` trailer, `git push --force` without `--with-lease`, and pushes to `main` |
| **PostToolUse on edits to DONE.md** | Check that a new entry's timestamp comes from the clock (within minutes of `date`), not an estimate |
| **PostToolUse on code edits** | Lint the edited file and feed errors back at once |
| **SessionStart** | Print the branch, `git status`, the open PR and the date, so a resumed session starts from facts |

Leave out hooks that commit, push or open PRs on their own (they would bypass the person's confirmation) and slow suites (end-to-end tests belong to the E2E runner).

### `justfile` and `utils/`: Markdown to PDF

Every Markdown document gets a PDF next to it (`foo.md` → `foo.md.pdf`):
- `just pdfs [PATHS]` builds a PDF for every Markdown file (all of them by default, `AGENTS.md`, `CLAUDE.md` and `.github/` excluded); `just pdf FILE` builds one; `just docs` is the same as `just pdfs`; `just clean` removes them.
- **Pipeline:** pandoc turns the Markdown into a standalone HTML page in a temporary directory (images embedded, math as MathML, Mermaid via `utils/pdf/mermaid.html`, LaTeX blocks typeset to SVG by `utils/pdf/latex.lua`), styled by `utils/pdf/style.css`; headless Chrome prints it to A4. The HTML is deleted.
- **Only what changed is rebuilt.** A PDF is rebuilt when its Markdown is newer than the PDF, or more precisely when the source or the build inputs (stylesheet, Mermaid include, LaTeX filter) changed: `.pdfstamps/` keeps a content hash of both the inputs and the PDF they produced, which survives the timestamp shuffling of `git checkout`. On a fresh clone without stamps, a PDF newer than its source and the build inputs is taken as current.
- **Structure:** the recipes live in the `justfile`; `utils/pdf/` holds `style.css`, `mermaid.html` and `latex.lua`. Generated `*.md.pdf` files and `.pdfstamps/` are ignored by Git.
- **Needs:** pandoc and Google Chrome; TeX Live only for documents with ```` ```latex ```` blocks.

Copy the document section of the `justfile` and `utils/pdf/`.

├── justfile             builds: documents now, the app later
├── LICENSE
├── .gitignore
├── .editorconfig
├── .github/
│   └── pull_request_template.md
├── docs/
│   ├── IDEA.md          purpose, users, added value, approach, innovation
│   ├── SPEC.md          stable requirements and acceptance criteria
│   ├── RESULTS.md       observed evaluation evidence
│   ├── agents/          role prompts, ownership and handoff contracts
│   ├── ARCH.md          architecture to be built
│   ├── EVAL.md          evaluation questions, comparisons, methods and criteria
│   ├── GAPS.md          open questions for the user, assumptions to check
│   ├── SEC.md           security implications, threats, controls by phase
│   ├── SDLC.md          development process (referenced by AGENTS.md)
│   ├── STYLE.md         code, UX and output style
│   ├── SBOM.md          software rules, toolchain, dependencies overview
│   ├── TODO.md          plan: milestones, tasks, subtasks
│   ├── ROAD.md          roadmap: phases with gates, unscheduled ideas
│   ├── DONE.md          progress log, newest first
│   ├── BOOT.md          this file
│   ├── design/          concept and approaches (upper case: central)
│   ├── assure/          assurance option: ASSR.md, generated lineage
│   ├── research/        research notes clarifying gaps (README.md: index, format)
│   └── input/           raw input, not edited (lower case)
├── utils/
│   └── pdf/             style.css, mermaid.html
├── <subproject>/        optional subproject (here assure/, semgit/)

│       └── EVAL.md      subproject's evaluation protocol, if needed

**Names:** upper case only for documents of central importance (`README.md`, `IDEA.md`, `ARCH.md`, `EVAL.md`, `SEC.md`, `GAPS.md`, `SDLC.md`, `STYLE.md`, `SBOM.md`, `TODO.md`, the design concept) or live assets that the build uses directly. Everything else is lower case: input, research, notes, study material, code.


## Gefly extension: orchestrator and specialist agents

This split is part of project setup, not an optional assurance add-on. Start with
an orchestrator and seven worker roles. [The workflow](agents/README.md) is the
operational contract; canonical prompts live in `docs/agents/`. Native project
agent registrations live in `.codex/agents/`, with global worker limits in
`.codex/config.toml`. The primary conversation acts as orchestrator through
AGENTS. These definitions do not launch persistent services.

| Role | Work | Deliverable and boundary |
| --- | --- | --- |
| **orchestrator** | Interact with the user, ask questions, record answers and assumptions, coordinate and integrate | Dated GAPS decisions, scoped dispatches, shared TODO/DONE updates and user reports |
| **researcher** | Background research; find and inspect web reference documents and data using available deep research skills | Assigned research notes and provenance/applicability/rights manifests; recommendations rather than decisions |
| **product** | Create/refine requirements and specification from user choices and research | Stable SPEC IDs and measurable acceptance criteria, scope and design changes |
| **code1** | Implement an agreed requirement slice and meaningful tests | Assigned implementation paths and reproducible check evidence |
| **code2** | Same responsibilities as code1; implement a separate slice in parallel | Disjoint paths against agreed shared contracts; equal implementation standards |
| **quality** | Independently check code output for quality criteria | Concrete correctness, maintainability, security, numerical and test findings |
| **validate** | Independently validate completed work against specification | Criterion-by-criterion expected/observed evidence and pass/fail/blocked/not evaluated |
| **housekeeping** | Maintain hygiene in parallel with implementation | Assigned documentation/tooling/inventory checks and changes, no scope or acceptance decisions |

The original brief's `coder1` means `code1`. Code2 is a separate stream, not the
quality reviewer. Research informs product; product establishes criteria before
implementation; quality and validate remain independent of implementation authors.
Researchers must disclose unavailable deep research skills and use a documented
primary-source fallback rather than claiming a tool ran. Preserve exact source
revisions, aircraft/configuration applicability, units and permitted data reuse.

### Dispatch, parallel work and integration

The orchestrator sends each worker a goal, TODO/requirement IDs, SPEC revision,
frozen acceptance criteria, dependencies, exclusive write paths, verification
commands and stop conditions. Agree shared contracts before concurrent code edits.
Run **code1 + code2 + housekeeping together** when capacity permits. With a
four-thread limit, that is the primary orchestrator plus three workers; schedule
research/product and review in other waves. Split tasks to respect lower limits.
Never let workers race on shared status files, contracts, manifests or lockfiles.
The orchestrator assigns one integration owner for them; workers return proposals.

After integration, quality reviews code and validate checks the specification at
the same stable artifact revision. Return failures to coders and repeat affected
checks after repairs or integration. An author cannot approve their own change by
switching role names. Missing evidence is blocked or not evaluated; unchecked work
is not a pass. Housekeeping runs alongside coding, not solely as a final cleanup.

Every return identifies role/task, reviewed revision or bounded working-tree
scope, changed paths, commands actually run, results, sources where relevant,
findings, open questions and limitations. Full dispatch/return templates and
canonical role links are in [the agent workflow](agents/README.md).

### Apply the guide to Gefly

The user selected a **Cessna 172**, **EASA PPL first** and a **web application
similar to GeoFS**; CPL follows later. Record the exact variant/year/avionics,
reference data, supported device/browser and first exercise before their dependent
implementation. See [GAPS](GAPS.md), [SPEC](SPEC.md) and [ARCH](ARCH.md). GeoFS is
an experience reference, not permission to reuse its code, data or assets.

Milestone 0 creates and checks the foundation. Runtime directories contain scope
notes until the stack is chosen. Use [TODO](TODO.md) for actual completed/open
items rather than treating the upstream example steps as proof of execution.
`LICENSE`, GitHub destination, commits, pushes and hosted CI follow the project's
recorded decisions and current user authorization; no remote or license is chosen
implicitly. Local checks work before a remote exists. The lightweight assurance
conventions are in [ASSR](assure/ASSR.md); the optional upstream tracker and hooks
have not been copied.

Subsequent user direction makes Gefly a **free/open-source flight-school community
project**. Propeller's private-repository command above remains an upstream
example, not Gefly's target visibility. The user-authorized public repository is
`gregoryyy/gefly`; exact project-wide licensing remains open. The roadmap also includes LLM-created flight experiences,
an EDDF/100 NM source-backed region and reuse-first open physics/models; current
scope and acceptance criteria remain authoritative in SPEC, ARCH and ROAD.
